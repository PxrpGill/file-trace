# Массовый перенос файлов с диска в file-trace

Разовый перенос большого объёма уже существующих файлов (например, при первом
внедрении file-trace или переезде с сетевого диска) — не то же самое, что
обычная загрузка через UI. Для этого есть отдельная CLI-команда
`import-tree`, которая пишет прямо в БД и в `FileStorage`, минуя HTTP API.

## Когда это нужно

Обычные пути загрузки — кнопка «Загрузить папку» (upload-tree) и загрузка
архива с «Распаковать» (extract-archive) — идут через `/api/` и упираются в
ограничения прод-nginx и самого API:

- `proxy_read_timeout 90s` в `frontend/nginx.conf` (выставлен под конвертацию
  LibreOffice, но действует на все `/api/` запросы) — длинная загрузка
  большого дерева файлов одним запросом легко в него не уложится и
  оборвётся, а поскольку у upload-tree одна транзакция на весь батч,
  ничего не запишется.
- `extract-archive` ограничен `MAX_TOTAL_UNCOMPRESSED_SIZE = 2 GiB` и
  `MAX_ENTRY_COUNT = 10_000` (`app/services/archive.py`) на один архив.

Для единичных папок/архивов в разумных пределах эти пути — штатный и самый
простой вариант. `import-tree` нужен, когда переносится действительно много
данных (условно — от нескольких ГБ/тысяч файлов и выше).

## Как это работает

`app/services/bulk_import.py` + подкоманда `import-tree` в `app/cli.py`:

- Использует те же хелперы, что и обычная загрузка (`app/services/tree_upload.py`),
  так что создаются точно такие же `File`/`FileVersion` и записи аудита
  (`file_upload`, `folder_create`), как если бы файлы загрузили через UI.
- Коммитит пачками (по умолчанию каждые 200 файлов), а не одной транзакцией
  на весь перенос — обрыв теряет максимум последнюю незакоммиченную пачку.
- **Идемпотентно**: если файл с таким именем уже есть в целевой папке, он
  пропускается. Прерванный перенос можно просто перезапустить той же
  командой — он продолжит с того места, где остановился, не задваивая
  уже перенесённое.
- По умолчанию пропускает системный мусор: `.DS_Store`, `Thumbs.db`,
  `desktop.ini`, `$RECYCLE.BIN`, `System Volume Information`, временные
  файлы офиса (`~$*`).
- Копирование байт на диск идёт в 4 потока параллельно (`--io-workers`),
  запись в БД — последовательно.

## Запуск

```bash
# сначала прикинуть объём, ничего не записывая
docker compose exec backend uv run python -m app.cli import-tree \
  /mnt/import --user ivan --root-name "Перенос с сетевого диска" --dry-run

# цифры устроили — запускаем по-настоящему
docker compose exec backend uv run python -m app.cli import-tree \
  /mnt/import --user ivan --root-name "Перенос с сетевого диска"

# или в уже существующую папку:
docker compose exec backend uv run python -m app.cli import-tree \
  /mnt/import --user ivan --folder-id 42
```

Параметры:

| Флаг | Назначение |
|---|---|
| `source` (позиционный) | Путь к директории-источнику |
| `--user` | Логин пользователя, от чьего имени будут записаны загрузка и аудит |
| `--root-name` | Создать новую корневую папку с этим именем (или `--folder-id`) |
| `--folder-id` | Перенести в уже существующую папку (или `--root-name`) |
| `--dry-run` | Только посчитать файлы/объём, ничего не писать |
| `--commit-every` | Файлов на один коммит (по умолчанию 200) |
| `--io-workers` | Потоков на копирование байт (по умолчанию 4) |

## Источник данных недоступен в контейнере напрямую

У backend-контейнера в `docker-compose.yml` смонтирован только том
`storage:/data/storage` — путь к источнику данных (диск хоста VM или
смонтированная сетевая шара) нужно прокинуть отдельно, временно на время
переноса:

```yaml
# docker-compose.yml, сервис backend
volumes:
  - storage:/data/storage
  - /mnt/import:/mnt/import:ro   # временно, убрать после переноса
```

```bash
docker compose up -d backend
```

`ro` — источник только на чтение, перенос ничего там не меняет.

## Если источник — сетевой диск (SMB/CIFS)

Монтируется на саму VM, где крутится file-trace, до прокидывания пути в
контейнер (см. выше):

```bash
sudo apt install cifs-utils
sudo mkdir -p /mnt/import

# credentials отдельным файлом — не в команде монтирования
# (иначе пароль попадёт в history/ps и в лог systemd)
sudo tee /root/.smbcredentials > /dev/null <<'EOF'
username=имя_пользователя
password=пароль
domain=домен_если_есть
EOF
sudo chmod 600 /root/.smbcredentials

sudo mount -t cifs //адрес-сервера/имя_шары /mnt/import \
  -o credentials=/root/.smbcredentials,vers=3.0,ro
```

## На что обратить внимание

- **Скорость упирается не только в пропускную способность сети.** SMB
  теряет в скорости в основном на количестве файлов — на каждый файл
  отдельное сетевое обращение (open/read/close), поэтому «объём / скорость
  канала» — это нижняя оценка времени, реальный перенос может быть
  медленнее при большом числе мелких файлов. Сначала `--dry-run`, чтобы
  увидеть реальное число файлов; сам перенос лучше запускать не в рабочие
  часы, так как источник и сама VM будут заняты продолжительное время.
- **Место на диске VM.** Под том `storage` должно быть достаточно свободного
  места под весь переносимый объём. Если не хватит и перенос упадёт на
  середине — не страшно: освободить место и перезапустить ту же команду,
  идемпотентность подхватит с места остановки.
- **Обрыв сети/VPN** во время переноса не страшнее обрыва самого скрипта —
  та же логика: перезапустить, он продолжит с недостающего.
- После переноса не забыть убрать временный bind-mount источника из
  `docker-compose.yml` и, если использовалась, размонтировать сетевую шару
  (`sudo umount /mnt/import`).
