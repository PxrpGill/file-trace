# Доступ к file-trace по локальному DNS-имени вместо IP

Как отдать file-trace на порту 80 и под человекочитаемым именем в локальной
сети (например `http://file-trace.alexa.local`) вместо `http://192.168.88.x:8080`.

## Что уже поддерживает сам file-trace

- **`frontend/nginx.conf` не фильтрует по имени хоста** — в конфиге нет
  директивы `server_name`, nginx отвечает на любой `Host`-заголовок.
  Неважно, зайти по IP или по кастомному DNS-имени — правки конфига не
  требуются.
- **CORS в бэкенде** (`app/main.py`) разрешает `http://localhost:5173` —
  это только dev-режим (vite на отдельном порту от API). В проде
  фронтенд и `/api/` отдаются одним nginx с одного origin, CORS тут не
  участвует независимо от имени хоста.

Значит вся работа — на уровне сети и docker-compose, а не в коде.

## Порт 80 вместо 8080

```bash
# .env
HTTP_PORT=80
```

`docker-compose.yml` пробрасывает `"${HTTP_PORT:-8080}:80"` — с
`HTTP_PORT=80` адрес будет без порта в URL. Бинд 80-го порта Docker делает
от root, дополнительных прав поднимать не нужно.

## DNS-имя на MikroTik (RouterOS)

DNS-сервер на MikroTik уже встроен — отдельный DNS-сервер поднимать не
нужно.

**1. Включить DNS-сервис и разрешить запросы от клиентов LAN:**

```
/ip dns set servers=8.8.8.8,1.1.1.1 allow-remote-requests=yes
```

`servers=` — upstream'ы для обычного интернета (то, что наверняка уже
настроено); `allow-remote-requests=yes` — без этой опции DNS роутера
резолвит только сам себя, а не отвечает на запросы других устройств сети.

**2. Добавить статическую запись:**

```
/ip dns static add name=file-trace.alexa.local address=192.168.88.x
```

**3. Проверить, что DHCP раздаёт клиентам сам роутер как DNS-сервер**
(обычно так по умолчанию, но стоит проверить):

```
/ip dhcp-server network print
# если dns-server пустой или не указывает на роутер:
/ip dhcp-server network set [find] dns-server=192.168.88.1
```

**4. Закрепить IP за VM с file-trace**, иначе при следующей выдаче адреса
по DHCP DNS-запись устареет:

```
/ip dhcp-server lease add address=192.168.88.x mac-address=<MAC VM> server=<имя dhcp-server>
```

(или выставить статический IP прямо на VM).

## Резолвинг для клиентов OpenVPN

Подключение по VPN не означает автоматически, что DNS-запросы клиента
пойдут через туннель — это настраивается отдельно. В RouterOS
OpenVPN-сервер работает через PPP-профиль, DNS раздаётся именно там:

```
/ppp profile set [find name=<имя-профиля-ovpn>] dns-server=192.168.88.1
```

VPN-клиентам нужно переподключиться, чтобы подхватить новый DNS-сервер.

## `.local` и mDNS — источник нестабильного резолвинга

`.local` зарезервирован под mDNS (Bonjour у Apple и аналоги — тот же
механизм, что резолвит принтеры/Chromecast в локалке). На **macOS**
`mDNSResponder` перехватывает резолвинг любых имён с `.local` и в первую
очередь пытается резолвить их через multicast вместо обычного DNS-запроса
к роутеру. Из-за этого статическая unicast-запись на MikroTik (см. выше)
может резолвиться нестабильно именно на маках — то работает, то нет.
Windows и Linux обычно ведут себя надёжнее, но тоже не гарантировано.

**Рекомендация:** не использовать `.local` вообще. Взять любую другую
зону, например `file-trace.test.lan` или `file-trace.test.internal` —
технически ничем не хуже, но не пересекается с зарезервированным
mDNS-неймспейсом. Вся настройка выше идентична, просто с другим именем в
`/ip dns static add name=...`.

## Опционально: HTTPS

Сейчас nginx слушает только `listen 80` (обычный http, без TLS) — JWT-токен
аутентификации (в localStorage, см. `CLAUDE.md`) ходит по сети в открытом
виде. В пределах доверенной локалки это обычно приемлемо; если понадобится
закрыть и это — нужен TLS-сертификат (внутренний CA или self-signed,
разложенный по доверенным хранилищам клиентов) и правка nginx под
`listen 443 ssl`. Отдельная задача, в этот документ не входит.
